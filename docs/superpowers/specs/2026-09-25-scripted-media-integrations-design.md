# JVM 媒体工作流动态接入设计（第二阶段）

日期：2026-09-25

状态：待用户审阅书面规格；依赖[第一阶段规格](./2026-09-25-media-capability-foundation-design.md)

## 1. 目标与适用范围

管理员给出有文档、可从自托管服务访问的工作流平台 HTTPS API 资料、账号凭证和允许接入的远端应用或工作流；接入 Agent 自动生成能力草案和 Groovy 钩子脚本。管理员审阅、用模拟响应测试并发布后，普通创作 Agent 才能在计划步骤中选择该能力。一个平台连接可发布多条用途不同的图片或视频能力。新增符合本设计约束的 RunningHub 类工作流平台及其工作流，应通过配置和发布完成，不改计划、审批、画布或 Java 平台适配代码。

支持自定义请求签名、鉴权交换、上传、提交、轮询、多步分支及结果映射。范围限于 HTTPS；浏览器交互、WebSocket、gRPC、任意本地协议、任意 URL 导入和服务器 Custom Node 安装不在本阶段。外部 API 必须有可固定的服务身份和可执行的输入输出约束；无法从文档与模拟测试证明语义正确的发布版本标记“未实测”，不能声称真实平台兼容。平台 API 若无可靠原请求核对手段，仍可接入，但提交不确定时保持 UNKNOWN。

第一阶段的 Mock/ComfyUI 内置适配器继续可用。OpenAI GPT Image 2 和 Google Nano Banana 2 是后续 BUILTIN 代码适配器，不使用本设计的 Agent 生成 Groovy 脚本；Seedance 等直接模型 API 也优先走 BUILTIN。普通 Agent 工具仍无任意 HTTP 或生成代码执行权；管理员审阅并发布的工作流能力才使用 ADMIN_GROOVY 路径。该例外是对旧 P0 “不得动态插件/任意 HTTP”约束的明确产品变更，实施时同步主规格、AGENTS.md、ADR 和检查清单。

## 2. 草案、审阅与发布

管理员在设置页新建或选中平台连接，输入精确 HTTPS 主机/路径范围与服务端加密凭证，提供 API 文档/OpenAPI 内容或受控文档链接，以及需要接入的远端应用、模型或工作流 ID。若平台提供列表/Schema 接口，管理员可授权只读发现以选择若干工作流；没有机器可读发现接口时由管理员提供文档和 ID。文档链接仅由管理员提交，经独立的公共 HTTPS 安全抓取器检查 DNS、重定向、大小与类型，不递归抓取，也不作为项目素材导入。文档及返回内容均视为不可信数据，只用于产生草案，不能指令 Agent 扩大权限。

接入 Agent 读取文档的安全摘要和脱敏测试反馈，为每条所选工作流生成独立草案：用途、主输出类型、类型化输入输出端口、参数约束、远端身份及版本/指纹检查、Groovy 钩子、请求地址/方法/路径允许列表、所需凭证与签名方式、费用来源、超时/并发上限、可核对/幂等声明及模拟响应夹具。它不能读取明文密钥、发布能力或发起付费测试。管理员在界面查看文档来源、生成源码差异、请求与凭证权限、输出数据流向以及脚本校验结果，可编辑草案；每次运行模拟测试前须先审阅并确认当前源码，Agent 不能自动执行草案脚本。

发布必须由管理员执行，要求 Schema/Groovy 脚本校验和模拟 API 测试通过；真实能力调用可选，不是发布门禁。发布生成不可变 media_capability_version，保存脚本源码 hash 与 Groovy 运行时版本、源文档摘要、审核者与时刻、模拟测试证据及 LIVE_VERIFIED 或 UNTESTED 标记。LIVE_VERIFIED 只能由记录了真实请求及结果的验收流程产生，管理员不能手工勾选。管理员更改 Groovy 脚本、工作流身份、端口或能力请求权限时须发布新能力版本；更改地址或凭证值须生成新连接版本，若同时改变能力允许的地址/凭证范围，还须发布新能力版本。旧版本保留供原任务核对；旧任务需要旧密钥时从历史密钥环读取，缺失则 BLOCKED。

远端可变工作流必须提供可核对的稳定版本、不可变 ID 或内容指纹；发布时固定并在新提交前检查。若平台不能提供任一种可验证身份，草案可保存但不能发布为可执行能力。管理员可停用能力以阻止新提交，已受理任务继续按原版本尝试核对。真实测试缺失不等于身份固定要求豁免。

## 3. Groovy 钩子与信任边界

管理员发布的 Groovy 脚本视为本地安装者信任的服务端扩展代码。脚本由 Spring Boot 主 JVM 中的 GroovyShell 执行，不要求沙箱、独立子进程或另一套部署。接入 Agent 只能生成草案，不能发布或直接运行真实平台请求；发布仍需管理员审阅和模拟测试。这里不声称脚本受到进程级隔离：发布后的代码拥有服务进程可访问的资源，管理员须像审查自编写的服务器代码一样审阅它。

每条脚本使用固定基类和版本化的 ctx API 实现 prepare、submit、query、reconcile、resolveOutput 等钩子，支持条件、循环、自定义签名和多步控制流。平台调用约定经 ctx.http(actionKey, request)；ctx 还提供签名/凭证、稳定时钟/nonce 和媒体句柄。钩子返回标准化的 COMPLETED、ACCEPTED、WAITING、REJECTED 或 UNKNOWN 结果。脚本的受支持用途是构造平台请求和映射结果；计划、Task、Asset、Artifact、用量与审批状态由应用服务修改，平台原始响应仍需校验。脚本在技术上能够绕过 ctx 使用 JVM API，因此 ctx 是接入契约，不是针对恶意管理员脚本的强制安全边界；绕过 ctx 的外部请求不享受动作账本的恢复保证。

GroovyShell 在现有 Java 21 JRE 上使用固定、经构建测试的 Groovy 依赖，无需 JDK 编译器。发布保存不可变脚本源码、摘要和 Groovy 版本；执行时使用独立 Binding，禁用运行时下载依赖的 @Grab/Grape。升级 Groovy 前须完成或处理使用旧版本的任务；无法在当前运行时安全重放的历史任务进入 BLOCKED，不换版本猜测重放。脚本执行槽位有上限，受管 HTTP 调用有超时；主 JVM 中的无限循环无法可靠强制终止，发生时管理员需要重启服务。[Groovy 集成文档](https://docs.groovy-lang.org/latest/html/documentation/guide-integrating.html)。

## 4. 受管 HTTP 与逐次动作账本

ctx.http 在主 JVM 中调用受管 HTTP 服务。服务按已发布的连接/能力版本检查管理员配置的主机、方法、路径、凭证范围、请求体/响应大小和媒体来源；逐次检查 DNS，默认拒绝重定向，媒体流式传输。ComfyUI 的精确本地地址例外不自动扩大到其他平台。脚本应将平台 HTTP、令牌交换、上传和结果下载都交给 ctx；直接使用 Groovy/Java 网络 API 属于不受支持的管理员代码，系统不能对它承诺地址检查或崩溃恢复。

每个 ctx.http 动作以 taskId、attemptNo、钩子调用序号和稳定 actionKey 形成唯一身份。发送前在短事务保存请求摘要、连接/能力版本、租约 epoch、关联键与动作类型；网络在事务外执行。返回后持久保存脱敏摘要及供重放的有界加密响应或暂存句柄。脚本重新运行时，同键同摘要的已完成动作回放结果，同键不同摘要为冲突；稳定时钟/nonce 由 ctx 按动作键提供。日志、诊断 API、SSE 不返回明文凭证或原始响应。

非幂等提交在调用后、持久确认前崩溃或超时，动作和 Task 进入 UNKNOWN；有可靠原请求 ID 时只核对原请求。查询为空不能证明未受理。无法核对时等待用户明确承担潜在重复费用，绝不由执行内核自动重提、换能力或运行下游。已保存 ACCEPTED 的动作只查原外部任务；查询、下载和归档可按原请求有限重试。旧 Worker 写入受 epoch 与状态 CAS 限制，取消后的晚到结果按原输入版本归档历史。多步流程中的上传、创建临时资源与生成提交都应各有检查点；某步不确定时不继续后续有副作用步骤。平台幂等需专门验证，不能仅凭模拟测试声明。

## 5. 计划使用、界面与 API

运行时 Agent 仅收到已发布能力的用途、适用输入输出、约束、成本来源和测试标记。它为每一步提出能力 ID 与端口绑定；沿用第一阶段的计划服务，并为 ADMIN_GROOVY 步骤额外固定脚本源码 hash 与运行时版本、输入版本和出站数据范围。用户逐步骤查看和确认，改选或补输入生成新计划修订；批准前不执行平台生成请求。若未实测，审批页与任务详情均显示该事实及费用未知时的风险。管理员发布、默认值更改不修改已经批准的步骤；被停用能力的未提交任务 BLOCKED，已受理任务仍按原版本核对。

管理员 API 增加草案创建、文档导入/受控发现、草案版本、Groovy 解析诊断、模拟测试、发布、停用及历史审计；项目 API 只暴露安全能力候选和逐步骤计划修订。所有修改受管理员身份、CSRF、Idempotency-Key 与 expectedVersion 约束；同键异载荷 409。项目 SSE 只发布计划/任务状态与脱敏能力摘要。同步更新 OpenAPI、Java DTO、生成的 TS 类型、Flyway、主规格、ADR 与部署备份说明。备份必须包含能力版本、不可变脚本源码与对应 Groovy 版本、动作账本、Asset 卷、主密钥和历史密钥环。

## 6. 验收与非承诺

用真实 PostgreSQL 和至少两种差异明显的本地假 HTTPS 工作流平台验收：一种同步图像并使用自定义签名，另一种多步上传/异步视频任务；再覆盖同一连接多工作流、动作迁移所需视频输入、文档注入不能让 Agent 自行发布、管理员操作鉴权、ctx.http 的地址/DNS/重定向与凭证检查、API/SSE/日志不泄漏密钥、同键请求冲突、并发审批、进程中断各检查点、UNKNOWN 人工核对、取消晚到、归档失败及 SSE 重连。测试只验证受支持的 ctx 路径，不宣称能阻止管理员发布的 Groovy 代码直接访问 JVM 资源或耗尽进程。模拟测试不能证明某真实供应商实际兼容。真实 RunningHub 类平台案例各自标注是否做过真实调用；未调用的一律保持 UNTESTED，不在验收报告中声称真实生成完成。GPT Image 2、Nano Banana 2 的真实协议验收属于各自 BUILTIN 适配器的后续工作。

本设计的“无需改代码”适用于可从自托管服务访问、能用受支持的 ctx HTTPS 动作与媒体端口表达、具有可固定远端身份的工作流平台 API。缺乏文档、只能浏览器操作、需要新媒体类型或不可固定远端定义的工作流，需要补充产品能力或暂不发布。例如，一个 RunningHub 连接可分别发布图像风格转换和动作迁移能力，固定各自的应用/工作流身份、输入端口与 Groovy 脚本版本；其 API 文档区分 Model、AI App 和 Workflow 调用类型，不能仅凭同一平台名称套用一种请求格式。[RunningHub API 文档](https://pre.runninghub.ai/runninghub-api-doc-en/)
