# 服装提取与自建服装参考库设计

状态：用户已基本确认，并明确修正为统一服装列表、后台区分来源；功能实现与验收另行记录。

## 用户已明确的需求

- 图片工具栏新增「服装提取」。输入图片，生成与示例相似的去人物服装展示图。
- 使用 OpenAI 图生图，同时提供统一样式参考图和提示词，以统一提取后的展示方式。
- 用户可以选择将提取结果加入服装参考库；提取本身不要求入库。
- 自建服装与三方服装在同一个列表浏览、搜索和使用，仅在后台区分来源与生命周期，删除三方来源或缓存不能影响自建服装。
- 自建库是实例级共享素材，所有登录会话可以浏览和使用。
- 当前产品只有单管理员，不新增用户列表、多账号管理或创建者协作流程；管理沿用现有管理员认证。

## 现有实现与方案选择

用户已指定 OpenAI 多图编辑路线。采用「独立图片后处理功能＋固定样式参考＋独立自建目录」，复用现有 Task、派生节点、媒体归档和参考应用服务。

现有 `OpenAiImage2Adapter` 已支持有序多图编辑，无需新增 Provider 或另一套模型执行器。`ImageOperation`、`MediaFunction` 和图片功能配置提供独立工具的注册与绑定位置。`DirectMediaTaskService` 已处理固定来源版本、命令重放、功能版本、能力版本和结果派生节点。

现有参考图库保存三方来源和不可变 Git 快照，其私有图片是可清理、可重建的来源缓存；这与用户主动保存的服装素材生命周期不同。自建目录放在 `referencecatalog` 领域内，通过应用服务使用独立归档，不伪装成 Git 来源或三方缓存。复用 `PrivateMediaArchive` 等现有媒体能力，但共享可见性由自建目录条目授权，不能直接开放底层归档路径。

两个未采用的做法：仅在智能编辑中预填提示词，虽然改动较少，但缺少稳定的专用入口与固定样式输入；将自建条目写入三方来源快照，会让来源同步和缓存清理影响主动保存的素材。二者均不适合本次需求。

## 产品行为

以下按已确认的方案实施，具体工程选择由实施者确定。

### 提取行为

1. 仅在图片节点当前展示已归档图片结果时提供「服装提取」，沿用已有图片工具栏和工具面板。
2. 默认提取主要人物的整套可见穿搭，包括上装、下装或连衣裙、外套、鞋袜、帽子、包和其他穿戴配饰。
3. 移除人物身体、皮肤、头发、脸部、环境、文字与非穿搭道具；输出保留服装体积的隐形人台效果。鞋袜和配饰按穿戴位置合理排列，使用统一浅灰摄影背景、柔和阴影和完整居中构图，默认竖幅 2:3。
4. 提供可选「提取说明」，用于指出多人图中的目标人物或限定需要保留的服装。没有说明时按主要人物处理；本次不新增人物框选、自动拆分单件或多轮识别流程。
5. 同一次调用固定待提取图片为 Image 1，样式参考为 Image 2。样式参考只控制背景、构图、摆放与光照，禁止把其中的款式、颜色、图案、鞋包等复制进结果。服装内容以 Image 1 为准。
6. 提示词允许为保持服装完整补齐必要的遮挡处，要求遵循原图可见结构，不声称不可见细节已被准确还原。固定参考和提示词提高一致性，不能作为真实模型效果已验证的依据。
7. 点击生成后，立即创建现有体系中的独立结果节点和持久图片生成任务。来源节点和内容保持各自的工作状态，结果通过现有派生关系追溯来源。
8. 完成后，用户可以在普通图片结果上选择「保存为服装参考」。该操作也适用于已有服装图片，便于手动建立参考库；不强制生成完成后弹窗，不自动入库。

### 固定样式与功能配置

- 新增 `COSTUME_EXTRACT` 图片操作和 `IMAGE_COSTUME_EXTRACT` 功能，沿用系统设置的模型绑定。首版仅绑定启用、支持至少两张参考图的现有 OpenAI 图片能力；不静默使用其他 Provider，也不从环境中猜测模型或 Key。
- 提取指令进入现有内置创作提示词管理，固定提示词版本。固定参考图使用随应用交付的合成示例及摘要，安装、启动和升级不调用外部模型。
- 合成示例应展示不同于验收输入的服装，方便检查是否错误复制了参考图中的衣物。不将用户附件或三方图库素材直接提交为内置资源。具体合成图在实施时生成、检查并随代码交付。
- 首版不新增样式参考图管理页面或逐次更换样式参考的控件，避免同一个工具输出不同展示标准。样式图版本和摘要与受理任务一起固定；后续替换内置样式不改变已受理任务。
- 功能未配置、模型停用或参考图容量不足时，沿用现有功能未配置/不兼容状态和管理员配置入口。Mock 只验证任务和素材流程，明确标注合成结果。

### 自建服装目录

- 服装参考使用同一个列表，合并自建与三方条目，统一搜索、分类、标签筛选、预览和应用。后台显式记录来源类型，自建图片独立归档且不属于任何三方来源快照或缓存。现有来源筛选继续可用，但不增加自建/三方切换页签。姿势目录继续使用原来源逻辑，不把服装新增为个人资产用途分类。
- 自建条目包含名称、可选分类、标签及一张不可变图片；首版不自动制造背面、侧面等未生成视角。服装提取结果和已有服装图通过同一保存入口建立条目。
- 入库先固定用户所选的精确图片版本，再将图片和缩略图独立归档。成功条目不依赖来源项目、来源节点或三方缓存存续。
- 浏览使用现有卡片、搜索、分类/标签筛选和图片详情的呈现习惯。自建元数据变更使用 CAS；允许管理员删除条目，删除后保留已导入项目内的独立副本。
- 当前单管理员负责新增、改名、分类、标签和删除。共享读取仍要求登录，管理仍要求现有管理员权限；保留项目来源校验，不能因共享目录而绕过来源项目访问授权。没有用户列表、成员选择或所有者管理 UI。
- 删除目录条目不删除原项目结果，也不删除已经导入其他项目的版本。条目图片不可原地替换；需要不同图片时另存新条目。

### 应用参考

- 自建和三方服装保持独立的读取/导入身份，前端可以复用展示组件和最终参考应用行为。
- 应用到图片或视频草稿时，将所选服装图片导入目标项目，取得目标项目自己的 Asset 与 ArtifactVersion，再通过现有草稿 CAS 追加。
- 保留已有提示词和媒体输入，沿用当前能力的模式、图片容量与工作流具名槽位校验。视频不隐式转换成首帧，不因选择参考而触发生成。
- 从资产页放到画布复用现有项目选择和显式放置流程。保存、导入与放置都有固定命令键；网络重试不能产生重复条目、图片或节点。

## 后端与持久化边界

- Controller、工具和前端操作通过应用服务协作。任务受理继续由 `DirectMediaTaskService` 负责，不在目录服务中调用 Provider。
- 受理时固定来源版本、可选说明、操作参数、样式参考身份/摘要、提示词正文/版本、功能绑定与能力版本，纳入重放比较及输入摘要。兼容已有历史命令，不通过更改旧任务补齐新字段。
- 样式图是应用自有输入，须通过内部不可变媒体准备路径加载；不能把文件路径或任意 URL 暴露成客户端可以指定的模型输入。不必为样式图创建可见的项目画布卡片。
- 本次扩展必须在后端与前端分别限制提取功能只能使用兼容的 OpenAI 多图能力。不能仅通过菜单禁用来保证协议正确，也不能放开所有图片操作的额外参考和蒙版约束。
- 自建目录使用独立条目、归档记录和幂等保存/导入记录；复用现有归档、校验、缩略图和命令恢复机制，避免新增无实际需要的通用执行框架。
- 文件读写和任何远程存储 I/O 在短数据库事务外执行；接受命令后使用稳定身份恢复归档和发布。中断或回执丢失只重放本次入库/导入，不能重新生成图片。
- 生成任务沿用排队、取消、失败、UNKNOWN、租约和晚到结果规则。UNKNOWN 只能由用户明确发起新的生成尝试，不能在查询、刷新或入库重试时触发生成。
- 新增 Flyway 迁移，不修改历史迁移；通过真实 PostgreSQL 重新生成 jOOQ。OpenAPI 是权威来源，先更新枚举/DTO/接口，再生成 TypeScript，不手改生成文件。
- 图片和 Key 沿用现有鉴权、服务端存储和日志边界。共享目录响应只返回可授权读取的接口，不返回底层存储路径、签名凭据或模型私有推理。

## 预计涉及的位置

- `frontend/src/features/canvas`：图片工具栏、提取面板、保存服装参考入口和任务反馈。
- `frontend/src/features/reference-catalog`：统一服装目录、后台来源隔离、自建条目管理，以及参考应用接入。
- `frontend/src/features/library` 与现有媒体参考选择器：按需要复用服装目录入口。
- `frontend/src/shared/mediaFunctions.ts`、API 客户端和四语言词典：功能注册、兼容性、请求和文案。
- `backend/src/main/java/dev/agenvas/task`、`provider`：专用操作、模型绑定、固定输入和重放校验；尽量复用 OpenAI 现有多图编辑协议。
- `backend/src/main/java/dev/agenvas/referencecatalog`、现有媒体归档应用服务：自建目录、独立图片与幂等保存/导入。
- `contracts/openapi.yaml`、新迁移、生成 TypeScript/jOOQ，以及固定样式资源和内置提示词。
- 实施后同步规格 §6.9、参考图库章节、领域说明、对应 ADR 和开发验收记录。

## 验证与交付

不运行全量测试作为基线。按改动运行下列专项验证，实际结果在实施完成后记录：

1. 操作和功能绑定单元测试：OpenAI、多图容量、未配置、停用、提示词版本和样式输入顺序。
2. 假 HTTP Provider 测试：实际请求包含来源与样式两张不同图片，顺序固定，提示词用途正确；这些测试不证明真实提取质量。
3. 真实 PostgreSQL 集成测试：来源 CAS、同键重放和异参冲突、任务输入快照、入库和导入幂等、并发保存、归档恢复、独立素材生命周期、登录/管理员/项目授权边界。
4. 前端定向测试：工具入口、说明保留、生成状态和失败恢复、可选入库、统一目录和自建/三方生命周期隔离、分类搜索、删除、应用参考容量/模式/草稿冲突。
5. TypeScript、相关 lint、四语言检查及契约检查；执行实际改动所要求的后端编译、生成代码检查和前端构建。浏览器检查桌面和窄屏的提取、保存与参考选择流程。
6. 如具备已授权的真实模型环境，单列真实 OpenAI 验证：不同原图使用同一参考样式，对照服装颜色/花纹/配饰保真、去人物、展示构图和参考服装泄漏。未实测时交付中明确写「真实 Provider 效果未验证」，不能用 Mock 或合成图片代替。

## 留给实施者的选择

可自行确定具体表名、DTO 分拆、组件抽取、已存在命令机制的复用粒度和定向测试组合，但必须满足上述归档、幂等、任务冻结、授权和单管理员边界。遇到实际代码不支持的假设时说明差异；不扩大为多用户系统、换装功能、单件分割平台或另一套媒体执行器。
